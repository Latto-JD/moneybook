# 계획서: 카테고리 색 고르기 (plan-category-color)

작성: planner / 작성일: 2026-11-17 / 기준: `af0e339` 작업 트리 (+ `plan-ux1` 진행 중)
사용자 요청 원문: "카테고리에서 색상도 변경 하게 해주면 좋겠네.. 신규로 추가했는데 계속 같은 색이야" (지출 카테고리 10개 사용 중)
표기: **[사실]** 코드에서 확인(파일:줄). **[권장]** 사용자 결정이 필요한 항목의 권장값(8장). 답이 없으면 권장값으로 진행한다.

---

## 1. 목표

카테고리마다 색·무늬를 저장해서 사용자가 카테고리 관리에서 바꿀 수 있게 하고, 새 카테고리는 아직 안 쓴 색을 자동으로 받게 해서 "계속 같은 색"이 다시 생기지 않게 한다.

## 2. 원인 (현재 상태)

- **[사실]** 색은 서버에 없다. `js/lib/viz.js:2-13` `stableVizMap` 이 유형별로 `sortOrder` 순(비활성 포함) 1~8번째에만 번호 1..8 을 주고, 9번째부터는 `vizOf` 가 `'none'`(`viz.js:16`)이다. `'none'` 은 테두리 회색·무늬 없음이다(`style.css:142`). 지출 10개면 9·10번째가 둘 다 회색이 된다.
- **[사실]** 팔레트는 8색이다. `tokens.css:45-52`(라이트), `:135-142`·`:159-160`(다크 두 곳), 견본 규칙 `components.css:122-129`, SVG 채움 `components.css:191-192`, 무늬 `patterns/viz-2..8.svg`, 차트 안 무늬 `charts.js:20-28` `VIZ_MARKS`. 1번은 단색이고 2~8번은 무늬가 있다.
- **[사실]** 색을 쓰는 곳은 모두 `stableVizMap`/`vizOf` 를 거친다: 기록 카테고리 칸(`record.js:213, 218`), 거래 목록 행 견본(`record.js:589`), 카테고리 관리 행(`category-manager.js:71, 86, 151`), 이력 머리줄(`history.js:71-72`), 대시보드 도넛·범례·범례 막대(`dashboard.js:31`, `charts.js:162-182`), 카테고리별 추이 막대(`dashboard.js:68`, `charts.js:299-311`).
- **[사실]** 도넛은 조각끼리 색이 겹치지 않도록 번호를 다시 고른다(`viz.js:22-38` `assignDonutViz`). 그래서 같은 카테고리라도 도넛과 다른 화면의 색이 다를 수 있다.
- **[사실]** 서버 카테고리 쿼리는 열 이름을 직접 적는다(`categories/routes.js:18` `ROW`, `lib/categories.js:76`). 그래서 열을 추가해도 구버전 코드는 그대로 동작한다. 반대로 새 코드가 `color` 를 읽는데 운영에 열이 없으면 500 이 난다. 그래서 **마이그레이션을 먼저 하고 푸시한다**(6장).
- **[사실]** 기록 탭 "카테고리별 수입/지출" 막대는 카테고리 색이 아니라 수입·지출 색이다(`record.js:465`). 이번에 바꾸지 않는다.

## 3. 사용자 스토리

- 사용자로서 카테고리 관리에서 카테고리 색을 골라 바꾸고 싶다.
- 사용자로서 새 카테고리를 만들면 다른 카테고리와 겹치지 않는 색이 자동으로 붙기를 바란다.
- 사용자로서 같은 카테고리는 기록·목록·이력·대시보드 어디서나 같은 색·무늬이기를 바란다.

## 4. 범위 / 범위 밖

**범위**
- `categories.color` 열 추가(nullable) + 기존 행 채우기, 운영 마이그레이션 1회(사용자 실행).
- API: 카테고리 객체에 `color`, `PATCH` 로 색 변경, `POST` 때 자동 배정.
- 팔레트 8 → 12색(**[권장]**, D1), 새 무늬 4개.
- 카테고리 관리 행에서 색 고르기.
- 색을 쓰는 모든 화면이 저장된 색을 쓴다(도넛 다시 고르기 제거 포함).

**범위 밖**
- 카테고리 추가 폼에서 색 고르기(자동 배정 후 행에서 바꾼다), 카테고리 순서 바꾸기(U7), 직접 색 입력(색상 선택기·hex), 기록 탭 수입/지출 막대 색, 월별 수입 대 지출 막대 무늬, `plan-ux1` 범위.

## 5. 설계

### 5.1 저장 (DB)

`schema.sql` 의 categories 블록 뒤에 추가한다(멱등):

```sql
-- v5: 카테고리 색·무늬 번호(1..12). null 이면 화면이 목록 순서 규칙으로 정한다.
alter table categories add column if not exists color smallint
  check (color is null or color between 1 and 12);
-- 비어 있는 행만 채운다: 유형별 sort_order, name 순 n번째 -> ((n-1) % 12) + 1
-- 1~8번째는 지금 화면 색과 같고, 9~12번째는 새 색 9..12 를 받는다.
update categories c set color = r.color
  from (select id, ((row_number() over (partition by user_id, type order by sort_order, name) - 1) % 12 + 1)::smallint as color
          from categories) r
 where c.id = r.id and c.color is null;
```

- 기본 세트 insert(`schema.sql:63-72`)와 `lib/categories.js` 의 기본 세트 생성(:63)은 `color` 에 배열 순서 + 1 을 넣는다. 방어용 insert(`schema.sql:76-89`)는 null 로 두고 위 update 가 채운다(update 를 그 insert 뒤에 둔다).
- 다시 실행해도 null 행만 바뀐다. 구버전 코드가 열을 모르고 만든 행(null)은 다음 마이그레이션이나 화면 규칙(5.3)이 처리한다.
- 정렬 동률의 이름 순서는 DB 정렬 기준을 따른다. 화면의 `localeCompare('ko')` 와 다를 수 있지만 `sort_order` 가 같은 행은 정상 데이터에서 드물고, 채운 뒤에는 저장된 값이 기준이 된다.
- 경로 비교: 마이그레이션 없이 하는 방법은 두 가지다. (a) 9번째부터 번호를 돌려쓰는 방법은 회색 문제만 고치고 고를 수는 없다. (b) 브라우저 저장소에 두는 방법은 기기마다 색이 다르다. 그래서 요청("변경하게")을 채우는 것은 DB 열 방식뿐이다.

### 5.2 API (`docs/api.md`, backend 가 구현 전에 먼저 고친다)

- 카테고리 객체(`api.md` 3A, 예 :223, 표 :232 부근)에 `color` 를 추가한다. 1..12 정수이며, 마이그레이션 전에 만든 행이면 `null` 일 수 있다. GET 목록 `items`, POST·PATCH 응답 모두 같다.
- `POST /api/categories`: 본문은 지금과 같다(`color` 를 보내도 무시한다). 서버가 색을 정한다. 같은 사용자·같은 유형의 **모든** 행(비활성 포함)에서 쓰는 번호를 빼고 남은 가장 작은 번호를 쓴다. 12개를 다 쓰면 가장 적게 쓴 번호 중 가장 작은 것을 쓴다. 같은 트랜잭션의 `lockUser` 아래에서 계산한다. 이렇게 하면 지출 10개 사용자의 다음 카테고리는 11번이 된다.
- `PATCH /api/categories/:id`: 본문에 `color`(1..12 정수)를 받는다. 이제 `name`·`active`·`color` 중 하나 이상이 필요하고, 여러 개가 오면 한 트랜잭션에서 처리한다. 정수가 아니거나 범위 밖이면 400 `VALIDATION_ERROR` 이고 `fields.color` 는 "색은 1~12 중 하나여야 해요." 이다. 같은 유형의 다른 카테고리와 색이 겹쳐도 허용한다(**[권장]** D2). 이름을 바꾸거나 사용 안 함으로 바꿔도 색은 유지한다(id 기준).
- 0장 변경 요약에 "추가: 카테고리 `color`, PATCH `color`. 응답 필드 추가라 호환. 운영 마이그레이션 필요." 를 적는다.
- 다른 API(거래·집계·인사이트·이력)는 바뀌지 않는다. 색은 화면이 카테고리 목록에서 이름으로 찾는다(지금과 같은 방식).

### 5.3 화면 공통 규칙 (`js/lib/viz.js`)

- `VIZ_COUNT = 12`.
- `stableVizMap(items, type)` 는 이름 → 번호 Map 을 만든다. `item.color` 가 1..12 이면 그 값을 쓰고, null 이면 5.1 과 같은 순서 공식 `((n-1) % 12) + 1` 을 쓴다. 9번째 이후가 회색이 되는 일이 없다.
- `vizOf` 의 `'none'` 은 목록에 없는 이름(삭제된 이름 등)에만 쓴다.
- `assignDonutViz`: 저장된 번호가 있으면 **겹쳐도 그대로** 쓴다(화면 간 일관성 우선). 번호가 없는 조각만 남은 번호를 쓴다. "그 외" 묶음은 지금처럼 `'other'` 다.
- 순수 함수 단위 테스트를 고친다(번호 우선, null 공식, 겹침 유지, 모르는 이름 'none').

### 5.4 팔레트 9..12 (**[권장]** D1: 12색)

- 이유: 지금 사용자는 지출 10개를 쓴다. 12색이면 겹치지 않고 2개가 남는다. 30개(활성 한도)까지 모두 구분되는 팔레트는 대비·구분이 무너져 현실적이지 않다. 12개를 넘으면 색과 무늬가 겹칠 수 있고, 이름·표로 구분한다.
- 추가 위치(사용자 요청으로 이미 원본과 달라진 파일, 메모리 기준):
  - `tokens.css`: `--viz-9..12` 를 라이트 1곳, 다크 2곳(미디어 쿼리 블록, `[data-theme="dark"]` 블록)에 추가한다. 각 값 옆에 이름·무늬를 적는다(기존 :45-52 형식).
  - `components.css`: `[data-viz="9".."12"]` 견본 규칙, `.viz-fill-9..12`.
  - `patterns/viz-9..12.svg`: 기존과 같은 8×8 mask 형식, 메타데이터·외부 URL 없음.
  - `charts.js` `VIZ_MARKS[9..12]`: svg 와 같은 모양.
- 색 조건(frontend 가 값을 제안하고 qa 가 잰다):
  - 라이트·다크 모두 카드 배경(`--color-surface`) 대비 3:1 이상.
  - 기존 8색과 색상(hue)이 겹치지 않는 계열을 쓴다. 후보는 주황, 분홍, 회청, 갈색이고, frontend 가 정한다.
  - 수입·지출 의미 색(`--color-income`/`--color-expense` 류)과 헷갈리지 않아야 한다.
  - `--viz-pattern-ink` 무늬가 그 위에서 보여야 한다.
- 무늬 4개는 기존 7종과 달라야 한다(예: X 교차, 큰 점, 지그재그, 굵은 대각 띠). 6px·8px 반복에서 서로 구분돼야 한다. 색만으로 구분하지 않는 원칙을 유지한다.
- 이름(스크린리더용): 기존 "하늘·무늬 없음, 밤색·사선, 겨자·점, 남보라·가로줄, 청록·격자, 와인·세로줄, 올리브·체크, 자두·역사선"에 새 4개를 같은 형식으로 붙인다. `lib/viz.js` 에 `VIZ_NAMES` 로 둔다.

### 5.5 카테고리 관리 화면: 색 고르기

- 행 동작 버튼에 "색"을 추가한다. 순서는 "색 · 이름 바꾸기 · 사용 안 함"(사용 안 함 행은 "색 · 이름 바꾸기 · 다시 사용")이다. 버튼 접근 이름은 "{이름} 색 바꾸기, 지금 {색 이름}" 이다.
- 누르면 그 행 아래에 고르기 영역이 펼쳐진다(이름 바꾸기 인라인 행과 같은 방식, 한 번에 한 행). `role="radiogroup"`, 접근 이름 "{이름} 색" 이다.
  - 12칸 견본은 각각 44×44px 이상이다. 360px 에서 6칸 × 2줄, 768px 에서 한 줄 또는 두 줄이다. 견본 안에 무늬가 보이고, 고른 칸은 체크 아이콘 + 굵은 테두리로 표시한다(색만으로 표시하지 않음).
  - 각 칸은 `role="radio"` 버튼이고 `aria-checked`, 접근 이름은 색 이름(예: "청록·격자")이다. 같은 유형의 다른 카테고리가 쓰는 색이면 이름 뒤에 ", 식비에서 사용 중" 을 붙이고 칸 아래에 작은 점을 표시한다. 고를 수는 있다(D2).
  - 키보드: 화살표로 이동(로빙 tabindex), Enter/Space 로 고르기, Esc 로 닫고 "색" 버튼으로 포커스를 돌려준다.
- 고르면 바로 `PATCH {color}` 한다. 진행 중에는 칸들을 `aria-disabled` 로 두고 포커스를 유지한다.
  - 성공하면 영역을 닫고 `#catm-status` 에 "'{이름}' 색을 {색 이름}(으)로 바꿨어요" 를 띄운다. 포커스는 그 행 "색" 버튼으로 간다. 목록을 다시 받고 `categorieschanged` 를 보내 다른 화면 색도 바뀐다.
  - 실패하면 행 오류(기존 `ui.rowError` 방식)를 보이고 영역은 연 채로 둔다.
- 행 견본(`swatch--lg`)은 지금처럼 보이고, 바뀐 색이 바로 반영된다. 안내문 "목록 순서대로 차트의 색과 무늬가 정해져요"(`index.html:163`)는 "색을 눌러 카테고리 색과 무늬를 바꿀 수 있어요" 로 바꾼다.

## 6. 운영 반영 순서 (사용자가 직접 실행)

연결 문자열·`.env.production.local` 내용은 채팅에 붙여넣지 않는다.

1. 로컬 검증 끝(qa 통과, reviewer "머지 가능"). 아직 푸시하지 않는다.
2. Neon 콘솔에서 **백업 브랜치**를 만든다.
3. `.env.production.local` 을 준비한다. `vercel env pull .env.production.local --environment=production` 로 받고, Neon Connect 창에서 **default 브랜치**와 **Connection pooling 끔**(주소에 `-pooler` 없음)인지 확인한다. 스크립트는 `DATABASE_URL_UNPOOLED` 를 먼저 쓴다(`migrate-prod.js:41`).
4. `npm run db:migrate:prod -- --yes` 를 실행해 "마이그레이션 완료" 줄을 확인한다.
5. Neon SQL 편집기에서 **default 브랜치를 골라** 아래를 실행하고 결과(숫자만)를 메인 세션에 알려 준다. "확인했어" 만으로는 진행하지 않는다.
   ```sql
   select column_name, data_type from information_schema.columns
    where table_name = 'categories' and column_name = 'color';
   select count(*) as total, count(*) filter (where color is null) as nulls,
          count(*) filter (where color between 1 and 12) as ok from categories;
   ```
   기대값: 첫 쿼리 1행(`smallint`), 둘째 쿼리 `nulls = 0`, `ok = total`.
6. 푸시한다(Vercel 배포).
7. 배포 확인: health 200, 로그인 후 `GET /api/categories` 의 `items[].color` 가 있다. 카테고리 관리에서 9·10번째 카테고리가 회색이 아니다.

- 호환: 열 추가는 구버전 코드에 영향이 없다(5장 사실). 마이그레이션과 푸시 사이에 구버전으로 만든 카테고리는 null 이다. 화면 공식(5.3)으로 보이고, 다음 마이그레이션 때 채워진다.
- 되돌리기: 코드만 되돌리면 된다(열이 있어도 구버전 동작). 열 삭제는 하지 않는다.
