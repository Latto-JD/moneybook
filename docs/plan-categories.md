# 카테고리 추가/수정/사용 안 함 기능 계획서 (plan-categories v1)

작성: planner / 작성일: 2026-10-20 / 상태: 초안 (16장 열린 질문 답변 대기. 답이 없으면 권장 기본값으로 진행)

## 0. 이 문서와 `docs/plan.md` 의 관계

- 이 문서는 운영 중인 moneybook(plan.md v2.1 기준 구현, 커밋 `22bbc17`)에 **카테고리 관리 기능과 "수입·지출 균형" 디자인 컨셉**을 더하는 **추가 계획서(addendum)** 다.
- `docs/plan.md` 는 **수정하지 않는다**. 이 문서에 적지 않은 내용(인증, 보안, R1~R5 상세, 기존 C1~C71/P1~P9)은 모두 plan.md 를 그대로 따른다.
- 카테고리 관련 내용이 plan.md 와 충돌하면 **이 문서가 우선**한다. 대체되는 plan.md 항목:
  - 3.2 제외 범위의 "사용자 정의 카테고리" → 이 문서 범위로 이동
  - 4.2 "고정 카테고리"와 transactions.category "해당 type의 고정 카테고리 중 하나" → 6장의 사용자별 카테고리 규칙
  - 6장 R1/R2/R4 정렬 동률의 "고정 순서" → 사용자 카테고리의 정렬 순서(6.6)
  - 7.3 "카테고리 칩", 7.4 D2/D4 → 9장, 11장
- 완료 기준 번호는 `C-C1…`(로컬), `P-C1…`(배포)로 새로 매긴다. 기존 C/P 항목은 회귀 검증 대상으로 유지한다(12.5 회귀 목록).
- 업무 흐름은 기존과 같다: planner → backend가 `docs/api.md` 를 **먼저** 갱신(B-C1) → frontend/backend 병렬 → qa → reviewer → 사용자 승인 하의 운영 반영(14장).

표기: **[사실]** = 저장소 코드에서 확인한 내용(파일:줄), **[가정]** = 확인하지 못했거나 정책 판단.

## 1. 목표

사용자가 수입·지출 카테고리를 직접 추가·이름 수정·사용 안 함/다시 사용할 수 있게 하되, 운영 DB의 기존 거래·통계·추천은 하나도 깨지지 않게 하고, 이 기능이 닿는 화면에서 수입과 지출이 동등한 비중으로 보이게 한다.

## 2. 현재 상태 조사 결과

### 2.1 카테고리 저장·검증 방식
| 항목 | 내용 |
|---|---|
| 저장 형태 | **[사실]** `transactions.category` 는 `text not null` 문자열이다. FK도, CHECK 제약도 없다 (`src/backend/db/schema.sql:34`). 카테고리 테이블은 없다. |
| 목록 정의 | **[사실]** 백엔드 상수 `CATEGORIES` (`src/backend/lib/categories.js:2-5`): 지출 8개(`식비, 카페/간식, 교통, 쇼핑, 주거/통신, 의료/건강, 문화/여가, 기타`), 수입 4개(`급여, 용돈, 부수입, 기타`). "기타"는 두 구분에 모두 있다. |
| 프론트 중복 정의 | **[사실]** 같은 목록이 `src/frontend/public/js/lib/validate.js:5-6` 에 하드코딩되어 있고, 기록 칩은 이 상수로 그린다 (`record.js:24`). `api.categories()` 클라이언트 함수는 있으나 화면에서 호출하지 않는다 (`api.js:92`, 호출처 없음). |
| 검증 | **[사실]** 거래 POST/PUT 은 `CATEGORIES[type].includes(category)` 로 검증 (`transactions/routes.js:31`). PUT 은 전체 필드 교체이며 기존 값과 비교하지 않는다. |
| 정렬 동률 | **[사실]** `categoryOrder()`(고정 배열 인덱스, 없으면 999)를 stats(`stats/routes.js:45,105`)와 R4(`rules/overspending.js:91`)가 사용. |
| 규칙의 카테고리 의존 | **[사실]** R1 그룹 키 `(category, 메모키)` (`quick.js:24`), R2 메모별 최다 카테고리 (`autocomplete.js:7-13`), R3 메모 없는 그룹 키 `(type, category, amount)` (`recurring.js:30`), R4 카테고리별 월 합계 (`overspending.js:32-39`), R5 같은 카테고리 비교군 (`large.js:11-19`). 모두 **문자열 동일성**으로 묶는다. |
| 집계 | **[사실]** stats/summary 는 `group by category` 문자열 그룹 (`stats/routes.js:36-39, 89-92`). 따라서 카테고리 목록에 없는 문자열도 집계에는 그대로 나온다. |
| 마이그레이션 | **[사실]** `npm run db:migrate` = `node --env-file-if-exists=.env src/backend/db/migrate.js` (`package.json:13`). `schema.sql` 전체를 `db.exec` 로 한 번에 실행 (`migrate.js:8-11`). pg 어댑터는 `pool.query(sql)` 단순 쿼리 (`pg.js:32`). |
| 마이그레이션 대상 선택 | **[사실]** `DB_DRIVER=pglite` 이면 무조건 PGlite, 아니면 `DATABASE_URL_UNPOOLED` → `DATABASE_URL` (`db/index.js:8-15`). 로컬 `.env` 에 `DB_DRIVER=pglite` 가 있으면 `npm run db:migrate` 는 **운영 DB가 아니라 로컬 PGlite** 에 적용된다. 출력의 `driver=` 로만 구분 가능 (`migrate.js:19`). |
| 문서 불일치 | **[사실]** README 5단계는 "`vercel env pull .env.local` 로 받은 값으로 `npm run db:migrate`" 라고 하지만 스크립트는 `.env` 만 읽는다 (`README.md:136` vs `package.json:13`). 지난 운영 마이그레이션을 실제로 어떻게 했는지는 **[가정: 확인 불가]**. |
| CSRF 대상 메서드 | **[사실]** `POST, PUT, DELETE, PATCH` 모두 Origin 검사·JSON 본문 파싱 대상 (`security.js:3`, `app.js:31-32`). |
| 운영 환경 | **[사실, 메모리 기록]** 운영(https://moneybook-psi.vercel.app)과 프리뷰가 **같은 Neon DB** 를 쓴다. 운영 DB에 실제 사용자와 QA 계정 거래가 있다. |

결론: 거래는 카테고리를 **문자열로** 저장하고, 규칙·집계도 전부 문자열로 묶는다. 이 구조를 유지하면 "사용 안 함" 카테고리의 과거 거래·집계·인사이트는 코드 변경 없이 계속 보인다.

### 2.2 차트·색 (카테고리 수 증가 영향)
- **[사실]** 도넛은 조각 i 에 `PALETTE[i % 8]` 과 `PATTERN_KINDS[i % 8]` 을 **같은 인덱스로** 준다 (`charts.js:13-14, 140-141`). 9번째 조각은 1번째와 색·무늬가 **완전히 같아진다**. 현재 지출 8개가 상한이라 드러나지 않았던 문제다.
- **[사실]** 도넛에 "기타 묶음" 로직이 없다. 모든 카테고리를 조각으로 그린다 (`dashboard-data.js:34-37`).
- **[사실]** 기본 카테고리 이름에 "기타"가 있으므로 묶음 조각 이름을 "기타"로 하면 사용자 카테고리와 충돌한다.
- **[사실]** D4 카테고리 추이 칩은 series 전체(sum>0)를 칩으로 그린다 (`dashboard.js:50`). 단일 막대이므로 색 충돌은 없다.

## 4. 범위 / 제외 범위

### 4.1 범위 (이번에 한다)
1. 사용자별 카테고리 저장(새 테이블), 기존 사용자·거래를 잃지 않는 멱등 마이그레이션
2. 카테고리 조회 / 추가 / 이름 수정 / 사용 안 함 / 다시 사용 API
3. 거래 생성·수정 검증을 사용자 카테고리 기준으로 변경 (사용 안 함 카테고리의 신규 선택 거부, 기존 거래 유지 수정 허용)
4. R1·R2 의 "새 입력용 추천"에서 사용 안 함 카테고리 처리, stats·R4 정렬 동률 기준 교체
5. 카테고리 관리 화면, 기록 칩의 동적 목록
6. 도넛의 "그 외 N개" 묶음과 색·무늬 중복 해소
7. **균형 컨셉 필수 변경**(11.2): 대시보드 카테고리 보기의 수입/지출 전환, 기록 탭 "카테고리별 수입", KPI 증감의 중립 색·대칭 문구, D3 막대 무늬 균형, 인사이트 문구 중립화
8. 운영 DB 마이그레이션 절차·백업·롤백 문서화 (README 보강)

### 4.2 제외 범위 (판단 근거)
| 제외 | 근거 |
|---|---|
| 물리 삭제 | 사용자 요구가 "삭제 = 사용 안 함"으로 명시. 문자열 저장이라 물리 삭제해도 거래는 남지만, 같은 이름 재생성 시 과거 거래와 의도치 않게 합쳐지는 문제(6.2)를 관리할 수 없게 된다. API에 DELETE 없음(405). |
| 사용 안 함 시 거래 재분류(다른 카테고리로 옮기기) | 요구는 "기존 항목 연동 유지"이며 재분류는 반대 방향. 비가역 일괄 변경이라 실수 복구 수단(undo)도 없다(plan.md 3.2 undo 제외). |
| 카테고리 병합 | 요구에 없음. 문자열 구조에선 일괄 UPDATE 1회로 가능하지만 되돌릴 수 없고, R3/R4 기준선이 합쳐져 인사이트가 바뀐다. 이름 수정이 기존 이름과 겹치면 409로 막는다(병합 방지). 후속 후보. |
| 순서 드래그 | 요구에 없음. 드래그는 360px 터치·키보드 대체 수단이 별도로 필요해 비용이 크다. 새 카테고리는 끝에 붙이고, 기본 세트는 기존 고정 순서 유지. 후속 후보: "위로/아래로" 버튼. |
| 아이콘/색 지정 | 요구에 없음. 사용자 지정 색은 대비 3:1·색각이상 원칙을 깨기 쉽다. 텍스트 우선 원칙 유지. |
| 카테고리의 수입↔지출 유형 변경 | 과거 거래의 type 과 카테고리 type 이 어긋나 집계가 깨진다. 유형을 바꾸려면 새로 추가. |
| 하위 카테고리, 카테고리별 예산 | 요구에 없음. 예산은 plan.md 에서도 제외. |
| 수입 쪽 R4/R5 대칭 인사이트(수입 감소 알림 등) | 규칙 신설은 범위 팽창. 11.3 후속 제안. |
| 순수지/저축률 신규 지표·차트 | 11.3 후속 제안. 기존 "잔액"(=수입-지출) KPI가 이미 있다. |
| 기본 카테고리 세트 변경(수입 기본 추가 등) | 16장 OQ-C12. 기본값은 "변경 안 함". |

| K2 | **이름 수정 = 같은 DB 트랜잭션에서 `categories.name` 과 해당 사용자·유형·옛 이름의 모든 거래 `category` 를 일괄 UPDATE**. 과거 거래도 새 이름으로 보인다. | 요구 "기존 항목까지 연동". R3/R4/R5 기준선이 이름 변경 후에도 이어진다(같은 문자열로 묶이므로). |
| K3 | **기본 카테고리는 사용자별 행으로 복사**한다(전역 기본값+오버레이 아님). 가입 시 복사, 기존 사용자는 마이그레이션에서 복사, 행이 0개인 사용자는 조회 시 지연 생성. | 오버레이는 "기본값 이름 변경/사용 안 함"을 별도 덮어쓰기 행으로 표현해야 해 모든 조회가 병합 로직을 거친다. 복사는 12행/사용자로 작고 단순하다. |
| K4 | 같은 유형 안에서 이름 정규화 키가 같으면 **활성/비활성 상관없이 중복**. 사용 안 함 상태의 같은 이름을 추가하면 **새로 만들지 않고 "다시 사용" 을 제안**(409 + id). | K1 때문에 같은 이름의 카테고리가 둘이면 거래 문자열이 구분되지 않아 자동으로 합쳐진다. 새로 만들기는 구조적으로 불가능하다. |
| K5 | 수입/지출 구분 유지. 카테고리 유형은 생성 후 변경 불가. 같은 이름이 두 유형에 각각 있는 것은 허용(현재 "기타"가 그렇다). | 2.1 사실, 4.2 근거 |
| K6 | 사용 안 함은 **새 입력에서만** 빠진다. 조회·집계·R3/R4/R5·대시보드는 그대로 포함. R1(빠른 입력)·R2(자동완성)는 새 입력용이므로 사용 안 함 카테고리를 제안하지 않는다(7.7). | 요구 해석 (2) |

## 6. 데이터 모델과 마이그레이션

### 6.1 새 테이블 `categories` (backend가 schema.sql·api.md 에서 확정)
| 필드 | 타입 | 규칙 |
|---|---|---|
| id | uuid | PK, `gen_random_uuid()` |
| user_id | uuid | not null, FK → users.id **ON DELETE CASCADE** |
| type | text | `expense` \| `income` (CHECK). 생성 후 불변 |
| name | text | 표시 이름(정규화 후 저장). 1~15자(코드포인트) CHECK |
| name_key | text | 중복 판정 키(6.2). not null |
| active | boolean | not null default true |
| sort_order | integer | not null. 유형별 정렬 순서 |
| created_at / updated_at | timestamptz | 서버 생성/갱신 |

- 제약/인덱스: `unique (user_id, type, name_key)` — **활성·비활성 모두 포함**(K4). 조회용 `(user_id, type, sort_order)`.
- transactions 테이블은 **변경하지 않는다**(컬럼·제약 추가 없음). FK를 걸지 않는 이유: K1, 그리고 이름 수정 시 FK가 있으면 갱신 순서 제약이 생긴다.

### 6.2 이름 규칙
1. 입력은 문자열이어야 한다(아니면 400).
2. 정규화(저장 값 `name`): 유니코드 NFC → 앞뒤 공백 제거 → 연속 공백(탭·줄바꿈 포함)을 공백 1칸으로.
3. 길이: 정규화 후 1~15 코드포인트. 제어 문자(U+0000–U+001F, U+007F)는 거부. 그 밖의 문자(`/`, `<`, 이모지 등)는 허용하되 프론트는 `textContent` 로만 출력(기존 원칙).
4. 중복 키 `name_key` = 정규화된 이름을 **소문자화**한 값(R 규칙의 메모 정규화 키와 같은 방식, `rules/common.js:4-9`). 예: `" Netflix  구독 "` 과 `"netflix 구독"` 은 같은 키.
5. 중복 판정 범위: 같은 사용자 + 같은 유형. 다른 유형의 같은 이름은 허용.
6. 사용 안 함 상태의 같은 키에 **추가** 요청 → 409 `CATEGORY_INACTIVE` + `error.categoryId`(그 카테고리 id). 클라이언트는 "다시 사용할까요?"를 묻고 PATCH `{active:true}` 로 복구(K4).
7. **이름 수정**의 새 키가 같은 유형의 **다른** 카테고리(활성/비활성)와 같으면 409 `CATEGORY_EXISTS`(병합 금지). **자기 자신과 같은 키**(대소문자·공백만 변경, 예: `netflix` → `Netflix`)는 허용하고 거래 문자열도 새 표기로 바꾼다.

### 6.3 이름 수정 시 기존 거래 반영 (K2 상세)
- 한 DB 트랜잭션(`db.transaction`, `pg.js:33-46`) 안에서: (1) 카테고리 행을 잠그고 옛 이름 확인 → (2) 새 이름 중복 검사 → (3) `categories` 갱신 → (4) `transactions` 중 `user_id = 세션 사용자 AND type = 그 카테고리 유형 AND category = 옛 이름` 을 새 이름으로 일괄 UPDATE.
- 다른 사용자, 다른 유형(예: 지출 "기타"를 바꿔도 수입 "기타"는 그대로)의 거래는 바뀌지 않는다.
- **경합 요구사항**: 이름 수정과 거래 생성/수정이 동시에 일어나도 "목록에 없는 옛 이름 문자열을 가진 새 거래"가 생기면 안 된다. 거래 쓰기 쪽은 카테고리 확인과 INSERT/UPDATE 를 같은 트랜잭션에서 카테고리 행 공유 잠금(또는 동등한 원자적 방법)으로 처리한다. 구현 방법은 backend 재량, reviewer가 코드로 확인(PGlite는 단일 연결이라 자동 테스트로 재현 불가 — 15장 위험).
- 규모 **[가정]**: 사용자당 수천 건 이하(plan.md 10장). 일괄 UPDATE는 사용자 행만 스캔하며 `(user_id, date)` 인덱스로 충분하다. 별도 인덱스는 추가하지 않는다.

### 6.4 기본 카테고리 처리 (K3 상세)
- 기본 세트는 현재 고정 목록과 **똑같다**(이름·순서): 지출 8, 수입 4. `sort_order` 는 0부터 기존 순서대로.
- **가입**: 사용자 INSERT 와 같은 트랜잭션에서 기본 12행 INSERT.
- **기존 사용자(마이그레이션)**: `categories` 행이 **하나도 없는** 사용자에게만 기본 12행 INSERT. "행이 하나도 없는" 조건이 핵심이다 — `on conflict do nothing` 만 쓰면, 사용자가 "식비"를 "밥"으로 바꾼 뒤 마이그레이션을 다시 돌릴 때 "식비"가 다시 생긴다.
- **지연 생성(안전망)**: 카테고리를 읽는 모든 경로(GET /api/categories, 거래 검증, R1/R2)에서 그 사용자 행이 0개면 같은 규칙으로 생성. 동시 요청은 unique 제약 + `on conflict do nothing` 으로 중복 없이 수렴. 이 안전망이 필요한 이유: 마이그레이션 후 ~ 새 코드 배포 전 사이에 **구버전 코드로 가입한 사용자**는 행이 없다.
- 기존 거래에 기본 목록 밖 문자열이 있을 경우 **[사실: 현재 검증상 생길 수 없으나 방어]**: 마이그레이션은 그런 (사용자, 유형, 문자열)마다 `active=false` 행을 만들어 관리 화면에서 보이고 다시 사용할 수 있게 한다. 이름이 15자를 넘거나 키가 겹치면 건너뛴다(거래는 그대로, 집계에도 그대로 보임). QA 운영 검증에서 이런 행이 0건임을 확인(P-C2).
- 기본 카테고리도 이름 수정·사용 안 함이 가능하다("기타" 포함). 단 **유형별 활성 카테고리는 최소 1개**(마지막 하나를 사용 안 함 → 409 `CATEGORY_LAST_ACTIVE`). 근거: 활성 0개면 그 유형의 기록이 불가능해진다.

### 6.5 개수 상한 근거 (K7)
- 유형별 활성 30개: 기록 칩은 드롭다운 금지(plan.md 7.3)라 모두 칩으로 펼쳐진다. 360px에서 한 줄 약 3~4칩 **[가정: 칩 폭 추정]** → 30개면 8~10줄로 한 화면을 넘기 시작하는 수준. 그 이상은 "2~3터치 기록" 목표(US-1)를 해친다. 현재 지출 8개의 약 4배로 개인 가계부에 충분 **[가정]**.
- 사용자당 전체 120개(비활성 포함): 물리 삭제가 없으므로 비활성 행이 계속 쌓일 수 있다. 무한 생성(남용) 방지와 관리 화면 목록 길이 제한. (활성 30 × 2 유형 + 비활성 여유 60)
- 이름 15자: 360px 칩·도넛 범례 한 줄(이름+금액+%) 수용. 기존 최장 이름 "카페/간식" 5자.
- 모두 코드 상수로 두어 조정 가능하게 한다(설정 UI 없음, plan.md Q4 원칙).

### 6.6 정렬 순서
- 기록 칩·관리 화면: `sort_order` 오름차순. 새 카테고리는 그 유형의 `max(sort_order)+1`. 다시 사용해도 원래 순서 유지.
- stats 동률·R4 동률: 그 사용자의 `sort_order`(비활성 포함), 목록에 없는 문자열은 맨 뒤, 그다음 이름 가나다순(`koCompare`). 기본 세트 사용자는 지금과 결과가 같다(C53 회귀 없음).

### 6.7 멱등 마이그레이션 요구사항
- `schema.sql` 에 추가 전용 SQL만 넣는다: `create table if not exists categories`, `create index/unique if not exists`, 6.4의 조건부 INSERT 2종(기본 세트, 방어용 비활성 행). 기존 테이블 ALTER/DROP 없음, transactions 쓰기 없음.
- 두 번 이상 실행해도 결과가 같아야 한다(C-C1, C-C3).
- 원자성 **[가정: 검증 필요]**: pg 단순 쿼리로 여러 문장을 보내면 Postgres는 하나의 암묵 트랜잭션으로 실행하므로 중간 실패 시 전체가 롤백된다. PGlite `exec` 도 같은지 B-C2에서 확인하고, 다르면 명시적 BEGIN/COMMIT 으로 감싼다.
- 마이그레이션 출력에 `driver=` 와 함께 "카테고리 행이 생성된 사용자 수"를 비밀값 없이 출력하도록 보강(B-C7). 운영 실행 시 `driver=pg` 확인이 대상 DB 오인 방지의 1차 수단이다.

### 6.8 운영 마이그레이션 실행 절차 (사용자가 직접 실행)
**사전 사실**: `npm run db:migrate` 는 `.env` 만 읽고, `.env` 에 `DB_DRIVER=pglite` 가 있으면 **로컬 PGlite** 에 적용된다(2.1). 그대로 실행하면 운영 DB에 아무 일도 일어나지 않은 채 "완료"가 출력될 수 있다.

권장 절차(PowerShell, 저장소 루트):
1. **백업**(CP-C1): Neon 콘솔 → 프로젝트 → Branches → 운영 브랜치에서 `backup-before-categories-<날짜>` 브랜치 생성(현재 시점 복사본). 브랜치 이름을 메인 세션에 알려 준다. 연결 문자열은 채팅에 붙여넣지 않는다.
2. **실행 전 기록**: Neon SQL Editor에서 `select count(*) from users;`, `select count(*), sum(amount) from transactions;` 결과를 적어 둔다(숫자만 보고).
3. **운영 환경변수 받기**: `vercel env pull .env.production.local --environment=production` (`.env*` 는 .gitignore 대상 — 커밋 금지).
4. **실행**: B-C7에서 추가할 `npm run db:migrate:prod -- --yes` 사용(권장, 16장 OQ-C16). 이 스크립트는 `.env.production.local` 만 읽고, `DB_DRIVER` 가 설정되어 있으면 거부하며, `--yes` 없이는 실행하지 않는다.
   - 스크립트를 추가하지 않기로 하면 대안: 로컬 `.env` 를 잠시 다른 이름으로 바꾼 뒤 `.env.production.local` 내용을 `.env` 로 복사해 `npm run db:migrate` 실행 → 끝나면 `.env` 를 삭제하고 원래 파일 이름 원복.
   - 어느 쪽이든 출력이 `마이그레이션 완료 (driver=pg)` 인지 확인. `driver=pglite` 면 **운영에 적용되지 않은 것**이다.
5. **실행 후 확인**: `select count(*) from categories;` = 사용자 수 × 12 (방어용 비활성 행 0건 가정), `select count(*) from users u where not exists (select 1 from categories c where c.user_id = u.id);` = 0, transactions 의 count·sum 이 2번과 같음.
6. 같은 명령을 한 번 더 실행해 오류 없음·행 수 변화 없음 확인(멱등).
7. 작업 후 `.env.production.local` 삭제 권장.

## 7. API 설계 초안 (확정은 backend가 `docs/api.md` 에서, B-C1)

공통: 기존 규약 그대로 — 세션 필수(없으면 401), 상태 변경은 Origin 필수(403)·JSON 전용(415)·16KB(413), 에러 형식 `{error:{code,message,fields?}}`, 다른 사용자 리소스·없는 id·UUID 아닌 id는 모두 404, 본문의 `userId`/`user_id` 등 알 수 없는 필드는 무시, 모든 쿼리 `user_id = 세션 사용자` 조건 + 파라미터 바인딩.

### 7.1 카테고리 객체
```json
{ "id": "uuid", "type": "expense", "name": "반려동물", "active": true, "sortOrder": 8, "usedCount": 3 }
```
`usedCount`: 그 사용자·유형·이름의 거래 건수(전 기간). 사용 안 함·이름 변경 확인 문구("기록 3건은 그대로 남아요")에 쓴다. 비용이 크면 backend가 생략을 제안할 수 있다(api.md에서 확정).

### 7.2 GET /api/categories (기존 경로, 응답 확장 — 하위 호환)
```json
{
  "expense": ["식비", "카페/간식", "교통", "쇼핑", "주거/통신", "의료/건강", "문화/여가", "기타", "반려동물"],
  "income": ["급여", "용돈", "부수입", "기타"],
  "items": [ { "id": "…", "type": "expense", "name": "식비", "active": true, "sortOrder": 0, "usedCount": 21 } ]
}
```
- `expense`/`income`: **활성** 이름만, sortOrder 순(기존 형식 유지 — 구버전 프론트가 캐시돼 있어도 동작).
- `items`: 활성+비활성 전체, 유형별 sortOrder 순.
- 행이 0개인 사용자는 이 시점에 기본 세트 생성(6.4).

### 7.3 POST /api/categories
요청 `{ "type": "income", "name": "이자" }` → **201** 카테고리 객체.
| 상태 | code | 상황 |
|---|---|---|
| 400 | `VALIDATION_ERROR` | type 이 expense/income 아님, name 이 문자열 아님·정규화 후 0자·16자 이상·제어문자 (`fields.type` / `fields.name`) |
| 409 | `CATEGORY_EXISTS` | 같은 유형에 같은 키의 **활성** 카테고리 |
| 409 | `CATEGORY_INACTIVE` | 같은 유형에 같은 키의 **사용 안 함** 카테고리. `error.categoryId` 포함 |
| 409 | `CATEGORY_LIMIT` | 유형별 활성 30개 또는 사용자 전체 120개 초과 |

### 7.4 PATCH /api/categories/:id
요청은 `name`, `active` 중 **1개 이상**(둘 다 있으면 이름 변경 후 상태 변경을 한 트랜잭션에서). `type` 은 받지 않는다(알 수 없는 필드처럼 무시). → **200** 갱신된 카테고리 객체.
| 상태 | code | 상황 |
|---|---|---|
| 400 | `VALIDATION_ERROR` | 두 필드 모두 없음, name 규칙 위반, active 가 boolean 아님 |
| 404 | `NOT_FOUND` | 없는 id / 다른 사용자 / UUID 아님 |
| 409 | `CATEGORY_EXISTS` | 새 이름 키가 같은 유형의 다른 카테고리(활성·비활성)와 같음 |
| 409 | `CATEGORY_LAST_ACTIVE` | 그 유형의 마지막 활성 카테고리를 사용 안 함 |
| 409 | `CATEGORY_LIMIT` | 다시 사용하면 유형별 활성 30개 초과 |
- 이미 같은 상태로 바꾸는 요청(active:true → true)은 200, 변화 없음(멱등).
- `PATCH` 는 이미 CSRF·본문 파싱 대상이다(`security.js:3`). 기존 api.md 의 "POST/PUT/DELETE" 표기를 PATCH 포함으로 고친다.
- `DELETE /api/categories/:id` 는 라우트를 두지 않아 405 `METHOD_NOT_ALLOWED`(Allow: PATCH).
- 검사 순서는 api.md 1.1 그대로(… → 인증 401 → 입력 검증 400 → 비즈니스 404/409).

### 7.5 거래 API 변경 (POST/PUT /api/transactions)
- category 검증: "해당 type의 **활성** 사용자 카테고리 이름과 정확히 일치"(정규화 없이 저장된 `name` 과 같은 문자열). 다른 사용자의 카테고리 이름은 당연히 불일치.
- **POST**: 사용 안 함 카테고리 → 400 `VALIDATION_ERROR`, `fields.category = "사용 안 함으로 바꾼 카테고리예요. 다른 카테고리를 골라 주세요."` 목록에 없는 이름 → 기존 문구 `"해당 구분에 없는 카테고리예요."`.
- **PUT**(사용 안 함 카테고리를 쓴 기존 거래 수정): 요청의 `(type, category)` 가 **그 거래의 현재 값과 같으면** 카테고리가 사용 안 함이든 목록에 없든 허용한다(금액·메모·날짜만 고치는 경우). 다른 카테고리로 바꾸려면 그 대상은 활성이어야 한다. 근거: 과거 기록의 금액 오타를 고치려고 카테고리를 강제로 바꿔야 하면 "연동 유지" 요구에 어긋난다.
- 응답 형식은 바뀌지 않는다.

### 7.6 조회·집계·인사이트에서 사용 안 함 카테고리
- GET /api/transactions, /api/summary, /api/stats/*, /api/insights 의 R3/R4/R5: **결과 집합 변경 없음**. 거래 문자열로 묶으므로 사용 안 함 카테고리도 계속 나온다(K6). 응답에 활성 여부 필드는 넣지 않는다(프론트가 7.2 `items` 로 판단).
- 정렬 동률 기준만 6.6으로 교체.

### 7.7 R1 / R2 응답 변화
- R1 quick: 카테고리가 **사용 안 함**인 그룹은 후보에서 제외(새 입력용 제안이므로). 목록에 없는 문자열(방어 케이스)도 제외. 제외 후 최대 5개.
- R2 autocomplete: `category` = 그 메모 그룹에서 가장 많이 쓴 **활성** 카테고리(동률은 최근). 그룹의 카테고리가 모두 사용 안 함이면 `"category": null`(계약 변경, api.md 명시). 메모·금액 제안은 유지. 프론트는 null 이면 카테고리를 채우지 않는다(현재 `applySuggestion` 이 목록에 없으면 채우지 않는 동작 `record.js:171` 과 같은 결과).
- 순수 함수 원칙 유지: 활성 카테고리 집합을 인자로 받는다(생략 시 필터 없음 → 기존 단위 테스트 호환).

## 9. UI/UX (frontend)

### 9.1 관리 화면 위치
- 해시 패널 `#categories` 를 새로 둔다. 하단 탭은 **2개(기록/대시보드) 유지**. 진입 경로: (a) 기록 폼 "카테고리" fieldset 오른쪽 "편집" 버튼(텍스트 버튼, 44×44px), (b) 대시보드 카테고리 영역의 "카테고리 관리" 링크. 패널 상단에 "← 기록으로" 버튼, 브라우저 뒤로가기로도 복귀. 근거: 자주 쓰지 않는 설정성 기능이 주 탭을 차지하지 않게 하고, 기존 해시 라우팅(`tabs.js`)을 재사용한다. 16장 OQ-C6.
- `tabs.js` 는 `categories` 를 패널로 인식하되 탭바 링크는 없음. 진입 시 패널 제목(h1)에 포커스.

### 9.2 관리 화면 구성 (360px 우선, 수입·지출 대칭 — 11.2-A)
```
[← 기록으로]                 카테고리 관리
( 지출 | 수입 )   ← 같은 크기의 세그먼트 토글. 초기값 = 기록 폼의 현재 유형
사용 중 9/30
 ├ 식비         21건   [이름 바꾸기] [사용 안 함]
 ├ …
새 카테고리 이름 [__________] [추가]
사용 안 함 (2)  ▸ (details, 접힘)
 ├ 경조사       4건    [이름 바꾸기] [다시 사용]
```
- 지출/수입 화면은 **같은 컴포넌트·같은 컨트롤·같은 상한·같은 문구 구조**. 유형별로 다른 것은 목록 데이터뿐.
- 행 버튼은 텍스트 버튼(아이콘만 금지), 각 44×44px 이상, 접근 이름에 카테고리명 포함("식비 이름 바꾸기").
- 360px에서 이름이 길면 줄바꿈(가로 스크롤 금지), 버튼은 다음 줄로 내려가도 됨.

### 9.3 흐름
| 흐름 | 동작 |
|---|---|
| 추가 | 입력 → [추가] 또는 Enter. 성공 시 입력 비움, 사용 중 목록 끝에 추가, `role=status` 로 "'반려동물'을 추가했어요", 포커스는 입력칸 유지(연속 추가). 409 `CATEGORY_INACTIVE` → 오류 영역에 "같은 이름의 사용 안 함 카테고리가 있어요." + [다시 사용] 버튼(누르면 PATCH active:true). 409 `CATEGORY_EXISTS`·`LIMIT` → 서버 문구 표시, 입력값 유지 |
| 이름 바꾸기 | [이름 바꾸기] → 그 행이 입력칸(현재 이름 채움, 전체 선택)+[저장][취소]로 바뀜. Enter=저장, Esc=취소. 입력칸 아래 고정 안내: "지난 기록 21건도 새 이름으로 바뀌어요." 성공/취소 후 포커스는 그 행의 [이름 바꾸기] 버튼으로 |
| 사용 안 함 | 확인 대화상자(기존 거래 삭제와 같은 `window.confirm` 방식 — `record.js:295`): "'경조사'를 사용 안 함으로 바꿀까요? 지금까지의 기록 4건과 통계는 그대로 남고, 새 기록에서만 고를 수 없어요." 확인 시 행이 "사용 안 함" 목록으로 이동, 포커스는 같은 위치의 다음 행(없으면 목록 제목). 취소 시 변화 없음 |
| 다시 사용 | 확인 없이 즉시(되돌리기 쉬운 동작). 사용 중 목록의 원래 순서 위치로 복귀 |
| 마지막 1개 | 그 유형의 활성이 1개면 [사용 안 함] 을 눌렀을 때 서버 409 와 같은 문구 "카테고리가 하나는 있어야 해요"를 보여 준다(버튼을 숨기지 않아 규칙을 알 수 있게) |

- 이중 제출 방어: 액션마다 진행 중 플래그(기존 `submitting` 패턴, `record.js:89-94`). 진행 중인 버튼은 `disabled` + 플래그로 Enter 경로까지 차단. 빠른 연속 클릭에도 요청 1회.
- 오류: 각 행/추가 폼 근처 `role="alert"` 텍스트, 필드 `aria-invalid`, 입력값 유지. 401은 기존대로 로그인 화면 이동.
- 변경 후 `categorieschanged` 이벤트 발행 → 기록 칩·대시보드가 다시 그린다. 기존 `datachanged`(대시보드 재조회)도 발행(이름 변경은 집계 이름을 바꾸므로).
- CSP: 인라인 `<script>`, `on*=` 속성, `style=""` 속성 금지. 마크업은 index.html 정적 + JS `el()`(`dom.js`)로 생성, 사용자 데이터는 `textContent` 만.

### 9.4 기록 화면 변경
- 카테고리 칩: 하드코딩 상수(`validate.js:5-6`) 대신 GET /api/categories 의 활성 목록. 앱 시작 시 1회 로드 + `categorieschanged` 시 갱신. 로드 실패 시 오류 문구와 [다시 시도] 버튼.
- 클라이언트 검증 `validateCategory` 는 목록을 인자로 받는다(순수 함수 유지, 테스트 가능).
- 수정 모드에서 거래의 카테고리가 사용 안 함(또는 목록에 없음)이면 그 이름을 **선택된 상태의 추가 칩**으로 맨 끝에 보여 준다. 칩 텍스트 "경조사 (사용 안 함)". 다른 칩을 고르면 이 칩은 사라진다. 수정 취소/저장 후에도 사라진다.
- 선택 중이던 카테고리가 관리 화면에서 사용 안 함이 되면 선택 해제.
- 빠른 입력(R1)·자동완성(R2)은 7.7 응답을 그대로 사용(null 카테고리면 비워 둠).

### 9.5 대시보드 차트 (카테고리 수 증가 대응)
- **도넛 최대 8조각**: 금액 내림차순 상위 7개 + 나머지를 합친 "**그 외 N개**" 1조각(나머지가 1개뿐이면 묶지 않고 8개 그대로). 이름을 "기타"로 하지 않는다(사용자 카테고리 "기타"와 충돌, 2.2). 묶음 조각은 전용 회색 + 전용 무늬(다른 조각과 겹치지 않는 조합).
- **색·무늬 조합 중복 금지**: 한 도넛 안의 모든 조각은 (색, 무늬) 조합이 서로 달라야 한다. 8조각 이하이므로 현재 8색 × 8무늬 배열로 충족(묶음 조각용 조합은 frontend가 정의).
- 범례: 최대 8행(그 외 포함), 각 행에 이름·금액·% 텍스트. "그 외 N개" 행 아래 묶인 카테고리 이름을 쉼표로 나열한 작은 텍스트.
- **표 대체는 묶지 않는다**: 모든 카테고리 행 + 합계. 색에만 의존하지 않는 원칙(텍스트·무늬·표) 유지.
- 요약 문장(svg desc)은 기존 형식 유지.
- 제목·중심 라벨은 11.2-B의 유형 전환을 따른다.
- D4 추이 칩: series 전체(sum>0). 칩이 많아도 줄바꿈으로 360px 가로 스크롤 없음.

## 11. 디자인 컨셉: 수입·지출 균형

사용자 요청(원문): "소비가 main처럼 느끼지 않도록. 소비와 수입에 발란스를 잘 유지되도록 컨셉."

### 11.1 원칙
1. **동등한 위상**: 이 기능이 닿는 화면에서 수입과 지출은 같은 크기의 컨트롤, 같은 조작 단계, 같은 정보 깊이로 제공한다. 한쪽에만 있는 화면 요소를 새로 만들지 않는다.
2. **가치 중립 색**: 유형(수입/지출)이나 증감 방향에 빨강=나쁨/초록=좋음을 쓰지 않는다. `--danger`(#b3261e)는 **오류 문구와 파괴적 버튼(삭제)에만**, `--ok`(#0b6b3a)는 유형·증감 표시에 쓰지 않는다. 수입/지출 구분은 파랑 계열 #0072B2 / 주황 계열 #C4500A(기존 팔레트, 흰 배경 대비 3:1 이상 유지)에 **무늬 + 텍스트**를 함께 쓴다.
3. **시각적 무게 균형**: 한쪽만 단색, 다른 쪽만 무늬처럼 잉크 양이 크게 다른 조합을 피한다. 수입 = 사선(`/`) 무늬, 지출 = 역사선(`\`) 무늬로 같은 밀도. 범례 텍스트 "수입 (/ 무늬)", "지출 (\ 무늬)".
4. **순서 규칙(일관성)**: 합계·요약·표·범례는 기존처럼 **수입 → 지출 → 잔액** 순(KPI·D3가 이미 그렇다). 입력 컨트롤(기록 폼·관리 화면·카테고리 보기 토글)의 유형 토글은 기존 기록 폼 순서 **지출 | 수입** 을 앱 전체에서 동일하게 쓴다(사용자 습관 유지, OQ-C13).
5. **대칭 문구**: 증감은 "늘었어요/줄었어요"로 수입·지출에 같은 동사를 쓴다. "썼어요", "과소비", "초과", ⚠ 같은 질책·경고 어조를 쓰지 않는다. 사용 안 함·오류 문구도 비난 없는 안내형.
6. 접근성 원칙은 그대로: 색에만 의존 금지(무늬·텍스트·표), 그래픽 대비 3:1 이상, 텍스트 대비 4.5:1 이상, 360px 가로 스크롤 없음.

## 14. 배포 계획

### 14.1 환경 위험
- **[사실]** 운영과 프리뷰가 같은 Neon DB. 프리뷰에서 테스트하면 **운영 DB에 쓴다**. 프리뷰 확인 단계가 운영 데이터 보호 장치가 되지 못한다.
- **[사실]** main 푸시 = 운영 자동 배포(plan.md 10장). 별도 승인 게이트는 푸시 승인뿐.
- 따라서 이번 변경은 (1) 스키마를 **추가 전용**으로 제한하고 (2) 운영 DB 변경 전 **백업 브랜치**를 만들고 (3) **마이그레이션 → 코드** 순서를 강제한다.
- 권장(OQ-C8): Neon에서 개발용 브랜치를 만들어 Vercel **Preview** 환경변수 `DATABASE_URL`/`DATABASE_URL_UNPOOLED` 만 그 브랜치로 바꾸면, 기능 브랜치 프리뷰에서 운영 데이터 없이 검증할 수 있다. 사용자가 원하지 않으면 현행 유지하고 프리뷰 단계는 생략(로컬 QA로 대체).

주의(코드 롤백 시): 새 코드에서 이름을 바꾸거나 새로 만든 카테고리로 기록된 거래는 문자열이 고정 목록 밖이다. 구버전 코드에서 이 거래들은 **조회·집계·인사이트는 정상**이지만(문자열 그룹), **수정(PUT) 시 구버전 검증에 걸려 400**이 된다(`transactions/routes.js:31`). 삭제는 가능. 롤백이 길어지면 사용자에게 안내한다. 이름 변경 자체를 되돌리는 자동 수단은 없다(필요 시 백업 브랜치의 값과 비교해 수동 UPDATE, 사용자 승인).
